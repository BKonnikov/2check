# Установка на сервер

Документ описывает первую установку 2check на VPS. HTTPS терминирует существующий HAProxy,
поэтому наружу приложение ничего не публикует — веб-интерфейс слушает loopback, а прокси
проксирует на него.

## Подготовка сервера

Проверено на AlmaLinux 9.8 (x86_64) с Docker 29.8 и Docker Compose 5.5. Для других дистрибутивов
семейства EL9 — Rocky, CentOS Stream, RHEL — шаги те же.

На минимальной установке AlmaLinux нет ни Docker, ни git. Ставятся так:

```bash
dnf -y install git
dnf -y install dnf-plugins-core
dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
dnf -y install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
systemctl enable --now docker
docker --version && docker compose version
```

Репозиторий Docker для CentOS покрывает всё семейство EL9. Обязателен именно пакет
`docker-compose-plugin` — команда `docker compose` через пробел. Старый `docker-compose` через
дефис этот файл не поймёт: в нём используются `profiles` и `depends_on.condition`.

Если `dnf` сообщит о конфликте с `podman`, `runc` или `buildah`, уберите их и повторите:

```bash
dnf -y remove podman runc buildah
```

SELinux мешать не будет: в compose используются только именованные тома, bind-mount'ов нет.

Ещё нужен HAProxy, уже обслуживающий `2check.uz` по HTTPS, — этот файл ничего наружу не
публикует и рассчитывает, что TLS терминируется выше.

## Проверка исходящей сети

Это самая важная проверка перед установкой, и её легко провести неправильно. Резолверы ходят по
**UDP** 53, поэтому проверка TCP-подключения к 53 порту ничего не доказывает.

```bash
dnf -y install bind-utils

# UDP 53 — то, что реально делает DNS-модуль
dig @8.8.8.8 uz +short NS
dig @9.9.9.10 uz +short NS

# RDAP по HTTPS — основной источник данных о регистрации
curl -s -o /dev/null -w "rdap=%{http_code}\n" https://rdap.cctld.uz/domain/cctld.uz

# WHOIS по TCP 43 — резервный источник
timeout 5 bash -c 'cat < /dev/null > /dev/tcp/whois.cctld.uz/43' && echo "порт 43 открыт"
```

Что должно получиться: оба `dig` возвращают список NS-серверов зоны, `rdap=200`, порт 43 открыт.

Как читать неудачи:

- **`dig` пустой или таймаут** — закрыт UDP 53. DNS-модуль не заработает, ставить дальше
  бессмысленно. Проверьте firewall и egress-правила.
- **`rdap` не 200** — недоступен основной источник регистрации. Модуль переключится на WHOIS,
  но проверьте, не блокирует ли исходящий HTTPS что-то посередине.
- **Порт 43 закрыт** — резервный WHOIS работать не будет. Не блокирует: RDAP основной, просто в
  редких случаях результат будет `registry_lookup_indeterminate` вместо данных.

Отдельно: пустой ответ `dig` на конкретный домен — это не сбой сети. У домена может не быть
записи такого типа или его может не быть вовсе. Проверяйте связность по заведомо существующей
зоне, например `dig @8.8.8.8 uz NS`, а не по произвольному имени.

Также нужен исходящий доступ к порту 443 проверяемых доменов — без него TLS-проверки вернут
«не удалось проверить».

## Конфигурация

Создайте `.env` рядом с `docker-compose.prod.yml`:

```bash
SITE_DOMAIN=2check.uz
WEB_PORT=3000

POSTGRES_USER=twocheck
POSTGRES_PASSWORD=<длинный случайный пароль>
POSTGRES_DB=twocheck

# PRD 27.2 — неизменяемый идентификатор выпуска. Меняется с каждой выкладкой.
APPLICATION_RELEASE_VERSION=1.0.0

LOG_LEVEL=info
```

Файл содержит секрет базы — права `600`, в репозиторий не попадает.

## Первая установка

```bash
docker compose -f docker-compose.prod.yml build
docker compose -f docker-compose.prod.yml up -d postgres redis
docker compose -f docker-compose.prod.yml --profile migrate run --rm migrate
docker compose -f docker-compose.prod.yml up -d api web
```

Миграции — отдельный шаг, а не побочный эффект запуска сервиса (§27.4). Выполняются под
advisory-блокировкой, поэтому одновременный запуск двух экземпляров схему не сломает.

Затем добавьте backend в HAProxy — образец в `deploy/haproxy.example.cfg`.

## Проверка после запуска

```bash
# Живость
curl -s http://127.0.0.1:3000/ru -o /dev/null -w '%{http_code}\n'

# Готовность: READY, DEGRADED или NOT_READY
docker compose -f docker-compose.prod.yml exec api \
  node -e "fetch('http://127.0.0.1:3001/readyz').then(r=>r.json()).then(d=>console.log(JSON.stringify(d,null,2)))"

# Манифест выпуска (§27.2) — по нему восстанавливается развёрнутая комбинация
docker compose -f docker-compose.prod.yml exec api \
  node -e "fetch('http://127.0.0.1:3001/release').then(r=>r.json()).then(d=>console.log(JSON.stringify(d,null,2)))"
```

`DEGRADED` означает, что недоступен Redis: сервис продолжает работать корректно, только медленнее
(§21.6). `NOT_READY` — недоступно или несовместимо хранилище сканирований, трафик подавать нельзя.

## Что проверить в первую очередь

Пять путей кода до установки ни разу не выполнялись на живой инфраструктуре. Проверьте их первыми
и именно в этом порядке:

1. **Миграции против настоящего PostgreSQL.** В тестах они прогонялись на встроенном экземпляре.
2. **Redis.** Адаптер не исполнялся ни разу. Сделайте два одинаковых сканирования подряд: второе
   должно пометить результаты как взятые из кэша.
3. **DNS.** Проверьте любой домен: резолверы должны вернуть записи, а не `UNKNOWN`.
4. **RDAP и WHOIS для `.uz`.** Самое вероятное место поломки — названия полей WHOIS взяты
   общепринятые, но с живым ответом `whois.cctld.uz` не сверялись. Если разбор не удаётся,
   результат будет `registry_lookup_indeterminate`, а не ложное «домен свободен».
5. **TLS.** Настоящее рукопожатие и разбор сертификата.

Инспектор помогает смотреть это без браузера:

```bash
docker compose -f docker-compose.prod.yml exec api node dist/cli/inspect.js example.uz
```

## Резервное копирование

Резервные копии делаются на уровне виртуальной машины — снимками ВМ. Это осознанное решение
владельца, а не то, что реализовано в приложении.

Что снимок ВМ покрывает: том `postgres-data` с историческими сканированиями. Что нужно понимать:
снимок берётся без остановки PostgreSQL, поэтому восстанавливается состояние на момент аварийной
остановки — база поднимется, но лучше дополнительно снимать логический дамп перед каждой выкладкой:

```bash
docker compose -f docker-compose.prod.yml exec postgres \
  pg_dump -U twocheck twocheck | gzip > backup-$(date +%F).sql.gz
```

Кэш Redis не является объектом резервного копирования (§27.8) и намеренно не сохраняется на диск.

## Выкладка новой версии

```bash
git pull
docker compose -f docker-compose.prod.yml build
docker compose -f docker-compose.prod.yml --profile migrate run --rm migrate
docker compose -f docker-compose.prod.yml up -d api web
```

Поднимайте `APPLICATION_RELEASE_VERSION` при каждой выкладке — по нему и манифесту определяется,
что именно развёрнуто.

## Откат

Откат приложения — пересборка предыдущего тега и перезапуск. Учтите §27.4: миграция может быть
необратимой. Перед разрушающей миграцией нужен дамп, иначе откат приложения не вернёт схему.
Исторические сканирования при откате не меняются (§27.7) — они неизменяемы на уровне базы.

## Что осталось незакрытым

- **Узбекский перевод написан Claude и не проверен носителем.** Каталог полный, ничего не
  блокирует, но текст для узбекского рынка стоит вычитать до широкой публикации.
- **Матрица браузеров, доступность и нагрузочные тесты (§26) не проводились.** По §26.8 это
  формально блокирует выпуск; решение о запуске без них принято осознанно.
- **Retryability из §17.6 не проброшен**: сервер не отдаёт признак повторяемости, и кнопка
  повтора в интерфейсе не может ему следовать (AC-23.6). Требует сначала определить таблицу
  политики §18.3.
- **Защита от злоупотреблений (§25.8) не реализована**: ограничения частоты, защита от
  злоупотребления FORCE_REFRESH и от перебора scanId. До публичного анонса это стоит закрыть —
  каждое сканирование это четыре DNS-запроса, обращение к реестру и TLS-рукопожатие.
