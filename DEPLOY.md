# Развёртывание и эксплуатация

**Русский** · [English](DEPLOY.en.md) · [На главную](README.md)

Руководство описывает развёртывание MVP 1.0 на одном VPS. HTTPS завершается на внешнем HAProxy. Локальный nginx передаёт запросы веб-контейнеру, опубликованному только на loopback. API, PostgreSQL и Redis доступны во внутренней сети контейнеров.

Почтовая категория MVP 1.1 ещё не реализована. Требования к её будущим SMTP-соединениям изложены в [PRD 1.1](docs/ru/03-prd-1.1.md).

## 1. Подготовка сервера

Предыдущая редакция фиксировала окружение AlmaLinux 9.8, Docker 29.8 и Docker Compose 5.5. Команды ниже предназначены для сервера семейства EL9. Совместимость конкретного окружения проверяется при установке; эта редактура не является повторным испытанием инфраструктуры.

```bash
dnf -y install git dnf-plugins-core
dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
dnf -y install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin nginx bind-utils
systemctl enable --now docker nginx
docker --version
docker compose version
```

Используется плагин `docker compose`. При конфликте пакетов сначала проверяется, используются ли установленные Podman, runc или Buildah другими сервисами; их удаление не является обязательным шагом установки.

В Compose используются именованные тома. Для соединения nginx с локальным портом при SELinux Enforcing требуется разрешение `httpd_can_network_connect`.

## 2. Входящий трафик

```text
Browser → HTTPS → HAProxy → HTTP → nginx :80 → 127.0.0.1:3000
```

Конфигурация nginx находится в `deploy/nginx.example.conf`. До её применения проверяются адреса HAProxy, адрес и порт назначения, а также передача `Host` и `X-Forwarded-Proto`. Доверенные адреса задаются через `set_real_ip_from` и должны соответствовать фактическим узлам прокси.

Пометка `default_server` относится к выделенному серверу приложения. При размещении нескольких сайтов конфигурация выбирается явно для каждого имени.

## 3. Исходящая сеть

Реализованный DNS-модуль использует UDP 53. Проверка TCP-порта 53 не подтверждает доступность его запросов. RDAP использует HTTPS, резервный WHOIS — TCP 43. TLS-проверкам нужен доступ к порту 443 проверяемых адресов.

```bash
dig @8.8.8.8 uz NS
dig @9.9.9.10 uz NS
curl -s -o /dev/null -w 'rdap=%{http_code}\n' https://rdap.cctld.uz/domain/cctld.uz
timeout 5 bash -c 'cat < /dev/null > /dev/tcp/whois.cctld.uz/43'
```

Ожидаются DNS-ответы с NS-записями зоны, успешный HTTP-ответ RDAP и успешное соединение WHOIS. Отсутствие ответа или тайм-аут требует проверки маршрутизации и правил исходящего доступа. Пустой DNS-ответ на произвольное имя сам по себе не доказывает сетевой сбой.

Недоступность RDAP проверяется отдельно от WHOIS. Работа одного источника не подтверждает доступность резервного.

## 4. Конфигурация

Создайте `.env` рядом с `docker-compose.prod.yml`. Пример содержит условный пароль; перед запуском его необходимо заменить.

```dotenv
SITE_DOMAIN=2check.uz
WEB_PORT=3000
POSTGRES_USER=twocheck
POSTGRES_PASSWORD=REPLACE_WITH_A_LONG_RANDOM_PASSWORD
POSTGRES_DB=twocheck
APPLICATION_RELEASE_VERSION=1.0.0
LOG_LEVEL=info
```

Файл содержит секрет базы данных, исключён из Git и должен иметь права `600`. `APPLICATION_RELEASE_VERSION` идентифицирует сборку; при обновлении используется идентификатор коммита.

## 5. Первая установка

```bash
chmod 600 .env
docker compose -f docker-compose.prod.yml build
docker compose -f docker-compose.prod.yml up -d postgres redis
docker compose -f docker-compose.prod.yml --profile migrate run --rm migrate
docker compose -f docker-compose.prod.yml up -d api web
```

Миграции выполняются явно до запуска новой версии API. Их конкурентный запуск защищён advisory-блокировкой. Затем установите проверенную конфигурацию nginx:

```bash
cp deploy/nginx.example.conf /etc/nginx/conf.d/2check.conf
setsebool -P httpd_can_network_connect 1
nginx -t
systemctl reload nginx
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: 2check.uz' http://127.0.0.1/ru
```

Команда `setsebool` нужна при SELinux Enforcing. После проверки локального маршрута настройте HAProxy на адрес ВМ и порт 80.

## 6. Проверка готовности

Веб-интерфейс, готовность API и манифест выпуска проверяются отдельно:

```bash
curl -s http://127.0.0.1:3000/ru -o /dev/null -w '%{http_code}\n'
docker compose -f docker-compose.prod.yml exec api node -e "fetch('http://127.0.0.1:3001/readyz').then(r=>r.json()).then(d=>console.log(JSON.stringify(d,null,2)))"
docker compose -f docker-compose.prod.yml exec api node -e "fetch('http://127.0.0.1:3001/release').then(r=>r.json()).then(d=>console.log(JSON.stringify(d,null,2)))"
```

`READY` подтверждает готовность обязательных компонентов. `DEGRADED` используется при недоступном Redis; `NOT_READY` запрещает подачу трафика из-за недоступного или несовместимого хранилища сканирований.

После установки проверьте миграции PostgreSQL, повторное использование кэша Redis, ответы DNS, RDAP/WHOIS для `.uz` и TLS-рукопожатие. Тесты на записанных данных не заменяют проверку доступности в целевой сети.

Инструмент для диагностики без браузера:

```bash
docker compose -f docker-compose.prod.yml exec api node dist/cli/inspect.js example.uz
```

## 7. Резервное копирование

Принятый способ резервного копирования — снимки ВМ с томом PostgreSQL. Возможность восстановления проверяется отдельно: наличие снимка само по себе не подтверждает восстановимость базы. Перед миграцией рекомендуется дополнительно сохранить логический дамп:

```bash
docker compose -f docker-compose.prod.yml exec -T postgres pg_dump -U twocheck twocheck | gzip > backup-$(date +%F).sql.gz
```

Redis содержит повторно используемый кэш и не является авторитетным объектом резервного копирования.

## 8. Обновление и откат

Штатное обновление:

```bash
./deploy.sh
```

Скрипт обновляет `main` без слияния расходящихся историй, устанавливает идентификатор выпуска, собирает образы, выполняет миграции, запускает приложение и ожидает готовности. Ручной эквивалент:

```bash
git pull --ff-only
export APPLICATION_RELEASE_VERSION=$(git rev-parse --short HEAD)
docker compose -f docker-compose.prod.yml build api web
docker compose -f docker-compose.prod.yml --profile migrate run --rm migrate
docker compose -f docker-compose.prod.yml up -d api web
```

Порядок обязателен: **сборка → миграции → запуск**. Идентификатор выпуска должен быть одинаковым для сборки, миграции и запуска. Новая версия API не готова принимать проверки, пока схема базы не совместима с ней.

Откат приложения выполняется пересборкой выбранного предыдущего выпуска. Он не отменяет миграцию автоматически. До применения разрушающей миграции определяются способ восстановления и допустимость отката. Исторические результаты сканирований сохраняют исходный смысл.

## 9. Известные ограничения

- Узбекский каталог подготовлен Claude; вычитка носителем в документации не подтверждена. Она остаётся отдельной задачей.
- Подтверждение полной матрицы браузеров, доступности и нагрузочных испытаний в этом руководстве отсутствует. Ранее был зафиксирован запуск без этих проверок; он не означает выполнения критериев PRD.
- Полная серверная модель `retryability` ещё не передаётся в результатах проверок. Задержка повтора при отказе в приёме запроса не заменяет эту модель.
- Ограничения частоты создания сканирований и общего параллелизма реализованы. Защита от перебора `scanId` и отдельная политика злоупотребления `FORCE_REFRESH` остаются предметом проверки перед расширением публичного доступа.

## 10. Ограничения нагрузки

| Параметр | Значение по умолчанию | Поведение |
|---|---|---|
| `SCAN_DEADLINE_MS` | `30000` | Общий срок сканирования. При исчерпании активное выполнение завершается с `completionReason=DEADLINE_TERMINALIZED`; незавершённые проверки получают `UNKNOWN` и `scan_deadline_exceeded`. |
| `SCAN_MAX_CONCURRENT` | `4` | Предел одновременно выполняемых сканирований; при превышении — HTTP 503. |
| `SCAN_RATE_LIMIT_PER_MINUTE` | `12` | Предел запусков на одного клиента за минуту; при превышении — HTTP 429. |

Эти переменные читает API. В текущем `docker-compose.prod.yml` они не передаются через `environment`; для изменения значений необходимо явно передать их контейнеру. Запись только в `.env` этого не делает.

Потерянное выполнение после перезапуска завершается как `FAILED` с `execution_state_unrecoverable`. Оно отличается от штатного завершения по общему сроку.

## 11. Адрес клиента и доверие к прокси

Ограничение частоты использует адрес клиента. nginx принимает `X-Forwarded-For` только от доверенных узлов HAProxy и передаёт приложению установленный адрес. Проверка извне:

```bash
curl -s https://2check.uz/api/whoami
curl -s -H 'X-Forwarded-For: 203.0.113.99' https://2check.uz/api/whoami
```

Оба ответа должны содержать действительный адрес клиента. Если произвольный заголовок меняет результат, проверьте всю цепочку HAProxy → nginx → приложение и конфигурацию доверия. Ограничение запросов на внешнем прокси дополняет защиту приложения.

## 12. Диагностика незавершённых проверок

Сначала проверьте готовность API, доступность базы и журнал:

```bash
docker compose -f docker-compose.prod.yml logs --tail=80 api
```

Сообщения `column does not exist` или `Storage schema version ... does not match` указывают на проблему схемы. Сверьте идентификатор сборки и выполненные миграции. После подтверждения причины используйте порядок обновления из раздела 8. Ошибка времени ожидания сама по себе не доказывает отсутствие миграции.

## 13. Статистика использования

Аналитика собирается самим сервисом в таблице `analytics_events`. Отчёт за 30 дней или за выбранный период:

```bash
docker compose -f docker-compose.prod.yml exec api node dist/cli/stats.js
docker compose -f docker-compose.prod.yml exec api node dist/cli/stats.js 7
```

Отчёт включает посещения, этапы проверки, просмотр результатов, технические подробности и отправку карточки. Домен, идентификатор сканирования, исходный ввод, IP-адрес и сведения о регистранте не принимаются в аналитические события.

Удаление событий старше 400 дней запускается явно. Значение выбирается по принятой политике хранения:

```bash
docker compose -f docker-compose.prod.yml exec api node dist/cli/stats.js --prune 400
```

## 14. Ограничения наблюдаемости адресов

Сканер может не иметь корректного маршрута к публичным адресам собственной инфраструктуры. Такой сетевой эффект нельзя интерпретировать как подтверждённый дефект домена.

Для известных адресов применяется `SECURITY_INTERNAL_DENYLIST`. Значение зависит от развёртывания; пример из существующей конфигурации:

```dotenv
SECURITY_INTERNAL_DENYLIST=91.216.37.0/24
```

Затронутые цели получают `UNKNOWN` с `ssrf_policy_block`. Изменение списка меняет `securityPolicyVersion`. Некорректное значение блокирует запуск; пустое не добавляет ограничений.

Список фиксирует ограничение наблюдения и не исправляет маршрут. Изменения hairpin NAT или маршрутизации проверяются отдельно инфраструктурной командой.
