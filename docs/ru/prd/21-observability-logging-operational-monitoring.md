# 21. Наблюдаемость, журналирование и мониторинг

<!-- nav:start -->
[Концепция](../01-concept.md) · [Оглавление PRD](../02-prd.md) · [English](../../en/prd/21-observability-logging-operational-monitoring.md)
<!-- nav:end -->

§21 определяет имена и структуру метрик, журналирование, готовность сервиса и правила оповещения.

## 21.1. Состояние платформы и здоровье домена

Наблюдаемость показывает, работает ли 2check; оценка здоровья домена описывает состояние проверяемой цели.

FAIL домена не означает автоматически ERROR платформы.

## 21.2. Связь событий

```text
requestId
→ scanId
→ moduleExecutionId?
→ operationId?
```

Совместная работа single-flight может иметь один moduleExecutionId для нескольких scanId.

## 21.3. Структурированные журналы

Имена событий устойчивы и ограничены заданным набором; пользователь не управляет именами событий.

Стандартные журналы не содержат:

- originalInput, путь или параметры URL;
- Authorization, Cookie или секреты сессии;
- персональные данные регистранта;
- исходное тело RDAP/WHOIS;
- значения внутреннего списка запретов.

## 21.4. Имена метрик

Имена в предшествующих разделах обозначают требования к сигналам; точные имена определяются в §21.

Канонические примеры:

```text
cache_lookup_total{module,outcome}
cache_bypass_total{module}
cache_write_error_total{module}
singleflight_join_total{module}
force_refresh_total{module?}
security_validation_total{decision}
ssrf_policy_block_total
security_validation_error_total
scan_started_total
scan_completed_total
scan_failed_total
```

Счётчики используют суффикс `_total`.

## 21.5. Число значений меток

Запрещены метки с неограниченным множеством значений:

- имя хоста;
- IP-адрес;
- scanId;
- requestId;
- отпечаток;
- внутренний CIDR.

## 21.6. Готовность сервиса

Сервис не готов, если невозможно безопасно принять сканирование, например:

- политика безопасности отсутствует или некорректна;
- обязательное хранилище доверенных сертификатов отсутствует или некорректно;
- обязательное хранилище сканирований недоступно или несовместимо.

Отказ внешнего RDAP/WHOIS/DNS-провайдера сам по себе не делает весь экземпляр сервиса неготовым.

Отказ Redis может соответствовать состоянию DEGRADED, если безопасный обход сохраняет корректность.

## 21.7. Оповещения

Основания для настройки оповещений:

- рост Web API 5xx/503;
- рост числа сканирований FAILED;
- сбои хранилища сканирований;
- активация или расхождение конфигурации и политики безопасности;
- внутренние ошибки проверки безопасности;
- всплески ошибок провайдера или ограничений частоты;
- аномальные задержки или исчерпание ресурсов.

Частота FAIL доменов по умолчанию не является основанием для срочного вызова дежурного.

## 21.8. Критерии приёмки

- **AC-21.1** Наблюдаемость платформы и здоровье домена разделены.
- **AC-21.2** §21 задаёт канонические имена метрик.
- **AC-21.3** Журналы структурированы; чувствительные данные исключены или скрыты.
- **AC-21.4** Значения цели с высокой кардинальностью не используются как метки метрик.
- **AC-21.5** Отказ внешнего провайдера не обязательно блокирует готовность.
- **AC-21.6** Некорректная политика безопасности блокирует готовность.
- **AC-21.7** FAIL домена не записывается как ERROR только из-за статуса FAIL.
- **AC-21.8** Историческая диагностика использует версии конкретного сканирования.
