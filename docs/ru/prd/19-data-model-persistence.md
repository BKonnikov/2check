# 19. Модель данных и хранение

<!-- nav:start -->
[Концепция](../01-concept.md) · [Оглавление PRD](../02-prd.md) · [English](../../en/prd/19-data-model-persistence.md)
<!-- nav:end -->

§19 определяет логическое хранение, классификацию данных и соотношение сроков их хранения.

## 19.1. Логические хранилища

```text
1. Scan Store
2. Reusable Cache
3. Sensitive / Gated Data Store
4. Operational Logs / Metrics
```

PRD не фиксирует технологию физического хранения.

## 19.2. Историческое сканирование

Запись выполнения PENDING/RUNNING может изменяться.

После COMPLETED/FAILED конечный снимок неизменяем.

Новое обновление создаёт новый scanId и не изменяет исторический снимок.

## 19.3. Сохраняемые данные

Снимок COMPLETED FULL сохраняет достаточно нормализованных данных для:

- CheckResults;
- CategoryResults;
- Issues;
- Summary;
- ScoreBreakdown;
- executionContext;
- необходимых технических метаданных аудита.

Исторический результат не пересчитывается по текущей политике.

## 19.4. Метаданные выполнения TLS

Каноническая структура:

```text
TlsExecutionMetadata {
  selectedIPv4?
  selectedIPv6?
  dependencyFingerprint
  securityPolicyVersion
  tlsModuleConfigVersion
  trustStoreVersion
  resultSource: FRESH | CACHE
}
```

Минимальные данные аудита предварительных условий: выбранные конечные точки, dependencyFingerprint и securityPolicyVersion.

## 19.5. Хранение сведений об актуальности

Сохраняются исходные `checkedAt`/`sourceUpdatedAt?` и признак происхождения `cached`.

`cacheAge` может вычисляться при чтении.

## 19.6. Исходный ввод — originalInput

По умолчанию не сохраняется в хранилище сканирований. Путь, параметры, фрагмент и учётные данные URL не относятся к сохраняемым данным здоровья домена.

## 19.7. Классификация данных

```text
PUBLIC_NORMALIZED
TECHNICAL_INTERNAL
GATED_SENSITIVE
OPERATIONAL_SECRET
```

Соответствие представлениям API:

- PUBLIC_NORMALIZED → Public;
- TECHNICAL_INTERNAL → явно разрешённое безопасное техническое представление;
- GATED_SENSITIVE → Gated;
- OPERATIONAL_SECRET → без представления в веб-API.

`TECHNICAL_INTERNAL` не означает автоматически ни доступность браузеру, ни исключительно серверное использование.

## 19.8. Данные регистрации

Публичное хранилище сканирований содержит нормализованные нечувствительные поля регистрации и только состояния полей регистранта.

Фактические значения регистранта и чувствительные исходные RDAP/WHOIS при необходимости хранятся в отдельном защищённом контуре.

## 19.9. Сроки хранения

Раздельные жизненные циклы устанавливаются для:

- ScanResult;
- кэша повторно используемых результатов;
- персональных данных с контролируемым доступом;
- исходных диагностических данных провайдера;
- журналов и метрик.

Точные сроки задаются политикой хранения данных, безопасности и архитектурными решениями.

Сохранение ресурсов сканирования не вводит пользовательскую функцию истории домена.

Основной идентификатор получения результата — `scanId`.

## 19.10. Целостность

COMPLETED публикуется только после атомарного сохранения согласованного конечного снимка.

ScorePenalty.issueId ссылается на существующий Issue. Ссылки Issue на проверки должны быть действительны в пределах того же сканирования и категории.

Представление в хранилище версионируется через `storageSchemaVersion`.

## 19.11. Критерии приёмки

- **AC-19.1** Назначение хранилища сканирований и кэша повторно используемых результатов разделено.
- **AC-19.2** Конечный снимок неизменяем.
- **AC-19.3** Историческая политика и оценка не пересчитываются.
- **AC-19.4** `originalInput` не сохраняется по умолчанию.
- **AC-19.5** Фактические персональные данные регистрации хранятся отдельно с контролируемым доступом.
- **AC-19.6** Доступность TECHNICAL_INTERNAL определяется списком разрешённых полей представления.
- **AC-19.7** OPERATIONAL_SECRET никогда не передаётся браузеру.
- **AC-19.8** Хранение не вводит неявную пользовательскую историю домена.
- **AC-19.9** Сохранение конечного результата атомарно и согласованно.
- **AC-19.10** Миграция схемы хранения не меняет смысл исторических результатов здоровья домена.
