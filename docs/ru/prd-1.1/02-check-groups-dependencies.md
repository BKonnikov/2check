# 2. Группы проверок и зависимость от MX

<!-- nav:start -->
[Концепция](../01-concept.md) · [Оглавление PRD 1.1](../03-prd-1.1.md) · [English](../../en/prd-1.1/02-check-groups-dependencies.md)
<!-- nav:end -->

§2 определяет внутреннее устройство категории `email`: на какие группы делятся проверки, какие из них зависят от `MX` и что происходит с каждой группой, когда почтового сервера у домена нет. Ответственный раздел для семантики статусов и зависимостей — 1.0 §7; здесь определяется только их применение к этой категории.

## 2.1. Три группы

```text
Email Authentication
├─ SPF
├─ DMARC
└─ DKIM

Inbound Mail
├─ MX
└─ STARTTLS

Mail Server
├─ PTR
└─ DNSBL
```

Группы не являются отдельными категориями и не имеют собственного вердикта: это единицы зависимости внутри одной категории.

## 2.2. Почему группы разделены

`SPF`, `DMARC` и `DKIM` — политики домена-отправителя, опубликованные как записи `TXT`. Они существуют независимо от того, принимает ли домен почту: запись `v=spf1 -all` на домене, который почту не отправляет и не принимает, — не ошибка, а корректное объявление.

`STARTTLS`, `PTR` и `DNSBL` описывают конкретный сервер. Этот сервер берётся из `MX`. Если записи `MX` нет, у этих проверок нет предмета — не результат неизвестен, а спрашивать не о чем.

## 2.3. Отсутствие MX

При отсутствии `MX`:

| Проверка | Статус |
|---|---|
| `SPF` | выполняется как обычно |
| `DMARC` | выполняется как обычно |
| `DKIM` | выполняется как обычно |
| `STARTTLS` | `NOT_APPLICABLE`, `blocked_by = mx_missing` |
| `PTR` | `NOT_APPLICABLE`, `blocked_by = mx_missing` |
| `DNSBL` | `NOT_APPLICABLE`, `blocked_by = mx_missing` |

`NOT_APPLICABLE`, а не `UNKNOWN`: `UNKNOWN` означает, что проверка применима, но результат получить не удалось, — здесь же отсутствует сам объект проверки.

Отсутствие `MX` оценивается один раз — проверкой `MX`. Заблокированные ею проверки штрафа не добавляют, иначе одна и та же причина наказывает домен четырежды. Правило снижения уверенности при `NOT_APPLICABLE` определяется в 1.0 §11 и здесь не меняется.

## 2.4. Принимающий сервер, а не исходящая почта

`MX` называет сервер, который почту для домена **принимает**. Сервер, с которого домен почту **отправляет**, может быть другим, и из публичных записей домена он не следует.

Поэтому результаты `PTR` и `DNSBL` формулируются как состояние принимающего сервера. Утверждения вида «письма этого домена будут попадать в спам» на основании этих данных не допускаются: они опираются на связь, которой в исходных данных нет. Общее правило о недопустимости недоказанных причинно-следственных утверждений — 1.0 §13.

## 2.5. Критерии приёмки

- **AC-2.1** Проверки `SPF`, `DMARC` и `DKIM` выполняются независимо от наличия `MX`.
- **AC-2.2** При отсутствии `MX` проверки `STARTTLS`, `PTR` и `DNSBL` получают `NOT_APPLICABLE` с `blocked_by = mx_missing`.
- **AC-2.3** Отсутствие `MX` не даёт `UNKNOWN` ни одной проверке категории.
- **AC-2.4** Отсутствие `MX` уменьшает числовую оценку один раз — результатом проверки `MX`.
- **AC-2.5** Сообщения проверок `PTR` и `DNSBL` описывают принимающий сервер и не утверждают ничего об исходящей почте домена.
