# 2. Группы проверок и зависимость от MX

<!-- nav:start -->
[Концепция](../01-concept.md) · [Оглавление PRD 1.1](../03-prd-1.1.md) · [English](../../en/prd-1.1/02-check-groups-dependencies.md)
<!-- nav:end -->

[§2](02-check-groups-dependencies.md#2-группы-проверок-и-зависимость-от-mx) определяет внутреннее устройство категории `email`: на какие группы делятся проверки, какие из них зависят от `MX` и что происходит с каждой группой, когда почтового сервера у домена нет. Ответственный раздел для семантики статусов и зависимостей — [1.0 §7](../prd/07-shared-status-dependency-category-scan-semantics.md#7-статусы-зависимости-и-результаты-сканирования); здесь определяется только их применение к этой категории.

## 2.1. Три группы

```text
Email Authentication
├─ SPF
├─ DMARC
└─ DKIM

Inbound Mail
├─ MX
└─ STARTTLS

Mail Server
└─ PTR
```

Группы не являются отдельными категориями и не имеют собственного вердикта: это единицы зависимости внутри одной категории.

## 2.2. Почему группы разделены

`SPF`, `DMARC` и `DKIM` — политики домена-отправителя, опубликованные в записях `TXT`. Их проверка не зависит от приёма почты. Например, запись `v=spf1 -all` может объявлять, что домен не отправляет почту.

`STARTTLS` и `PTR` проверяют принимающий сервер, определённый по записям домена. Если такого сервера нет, эти проверки неприменимы.

## 2.3. Что считается принимающим сервером

Отсутствие `MX` не означает, что почту домену доставить некуда. RFC 7505 описывает порядок, установленный RFC 5321: не найдя `MX`, отправитель обращается к адресным записям самого домена. Такой сервер называется неявным, и предмет у проверок принимающего сервера при этом есть.

Предмета нет в двух случаях:

| Состояние домена | Значение `blockedBy` |
|---|---|
| нет ни `MX`, ни адресных записей | `mx_missing` |
| опубликован `MX` вида «почту не принимаю» | `null_mx` |

Второй случай — осознанное заявление владельца по RFC 7505, а не упущение. Подробности обоих — [§6](06-mx.md#6-mx).

## 2.4. Когда предмета нет

| Проверка | Статус |
|---|---|
| `SPF` | выполняется как обычно |
| `DMARC` | выполняется как обычно |
| `DKIM` | выполняется как обычно |
| `STARTTLS` | `NOT_APPLICABLE` с `blockedBy` |
| `PTR` | `NOT_APPLICABLE` с `blockedBy` |

`NOT_APPLICABLE`, а не `UNKNOWN`: `UNKNOWN` означает, что проверка применима, но результат получить не удалось, — здесь же отсутствует сам объект проверки.

Отсутствие принимающего сервера оценивает проверка `MX`. Заблокированные проверки не добавляют штрафов. `NOT_APPLICABLE` не снижает уверенность; правила полноты и уверенности из [1.0 §7](../prd/07-shared-status-dependency-category-scan-semantics.md#7-статусы-зависимости-и-результаты-сканирования) и [1.0 §11](../prd/11-domain-health-summary-issues.md#11-сводка-технического-здоровья-и-выявленные-проблемы) сохраняются.

## 2.5. Принимающий сервер, а не исходящая почта

`MX` называет сервер, который почту для домена **принимает**. Сервер, с которого домен почту **отправляет**, может быть другим, и из публичных записей домена он не следует.

Поэтому результаты `PTR` формулируются как состояние принимающего сервера. Утверждения вида «письма этого домена будут попадать в спам» на основании этих данных не допускаются: они опираются на связь, которой в исходных данных нет. Общее правило о недопустимости недоказанных причинно-следственных утверждений — [1.0 §13](../prd/13-human-readable-messages-localization.md#13-пользовательские-сообщения-и-локализация).

## 2.6. Критерии приёмки

- **AC-2.1** Проверки `SPF`, `DMARC` и `DKIM` выполняются независимо от наличия `MX`.
- **AC-2.2** При отсутствии `MX`, но при наличии адресных записей домена проверки принимающего сервера выполняются против неявного сервера.
- **AC-2.3** При отсутствии предмета проверки `STARTTLS` и `PTR` получают `NOT_APPLICABLE` с `blockedBy` из значений `mx_missing` и `null_mx`.
- **AC-2.4** Само отсутствие принимающего сервера не является причиной `UNKNOWN` для проверок категории.
- **AC-2.5** Состояние принимающего сервера уменьшает числовую оценку один раз — результатом проверки `MX`.
- **AC-2.6** Сообщения проверки `PTR` описывают принимающий сервер и не утверждают ничего об исходящей почте домена.
