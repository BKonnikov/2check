# 2check.uz — концепция портала для проверки доменов

**2check_Product_Concept_v1.0 — FINAL / FROZEN**

## 1. Позиционирование

**2check.uz — проверка технического здоровья домена простым языком.**
DNS, домен, SSL, почта и безопасность — в одном месте. Для специалиста — исходные данные. Для обычного пользователя — что сломано и как исправить.

**Аудитория — два слоя:**
- Технические специалисты — точные данные, raw-вывод, экспорт
- Новички / владельцы бизнеса — понятные вердикты на человеческом языке

**Главный экран:**
```
Проверьте домен
[ example.uz________________ ] [ Проверить ]
```

**Результат — Domain Health Summary.** Главный элемент — не число, а человеческий вердикт; score — вспомогательная визуализация рядом с ним, не наоборот. Пример ниже — экран **MVP 1.0** (без Email — этот блок появляется в Summary после MVP 1.1):

```
Есть проблемы
1 критическая • 1 рекомендация

87/100

DNS          ✅
  A          ✅ обнаружена
  AAAA       ✅ обнаружена
Домен        ✅
SSL/TLS      ❌
  IPv4       ✅ TLS-соединение устанавливается
  IPv6       ⚠️ TLS-соединение не устанавливается
```

Если сделать 87/100 главным элементом — неизбежно возникает классический вопрос "почему именно 87, а не 86". Текстовый вердикт первичен, число — контекст.

IPv4/IPv6 разнесены по смыслу, но не выделены в отдельный scope-модуль: DNS-модуль отвечает только за resolver comparison (нашлась ли запись A/AAAA), а IPv4/IPv6-результат TLS-соединения показывается как часть уже существующего **SSL/TLS check** ("TLS-доступность"), а не как новый универсальный чек "доступности сайта" — такой формулировки в scope MVP 1.0 нет, и не стоит создавать неоднозначность, будто нужен отдельный TCP/connectivity-модуль. AAAA, которая корректно резолвится, но не даёт установить TLS-соединение — это не сломанный DNS, а результат SSL/TLS check по IPv6; называть это проблемой DNS неточно.

## 2. Статус, severity и Domain Health Score

### 2.1 Разделение status / severity

Это две независимые оси, не одна:

```
status   = PASS | FAIL | UNKNOWN | NOT_APPLICABLE
severity = critical | warning | informational | none
```

`status` — факт: выполнено условие проверки или нет. `severity` — потенциальный уровень воздействия, если чек даёт отрицательный результат (точная формулировка уточняется в PRD; текущего уровня детализации в Concept достаточно). Это две по-настоящему независимые оси — `INFO`/`WARN` не входят в `status`, потому что они уже являются severity, и попытка держать тяжесть проблемы одновременно в обоих местах рано или поздно создаст противоречивые комбинации вроде `status=WARN` + `severity=critical`, где непонятно, какая ось источник истины.

Примеры:
```
DMARC отсутствует     → status = FAIL, severity = warning
AAAA отсутствует       → status = FAIL, severity = informational
                          (или status = PASS, если отсутствие AAAA
                          в принципе не считается дефектом, а лишь
                          отсутствующей рекомендованной записью)
```

`UNKNOWN` и `NOT_APPLICABLE` — два разных состояния, которые не стоит смешивать:
- `UNKNOWN` — проверка технически применима, но не удалось получить результат (RDAP timeout, blacklist API недоступен). "Мы не знаем, потому что не смогли проверить."
- `NOT_APPLICABLE` — проверка в данном случае концептуально не имеет смысла, потому что её объект отсутствует (например, MX-запись отсутствует → сам вопрос "поддерживает ли этот MX STARTTLS" не имеет объекта проверки). "Проверять нечего."

Оба статуса не участвуют в штрафе score (раздел 2.3), но помечаются на UI по-разному: `UNKNOWN` — "часть проверок не завершена", `NOT_APPLICABLE` — просто не показывается как проблема (серый/нейтральный, не жёлтый/красный).

**`blocked_by` и `reason_code` — разные атрибуты, не взаимозаменяемые:**
- `blocked_by` используется **только** если чек не выполнен вследствие состояния другого чека (зависимость между проверками):
  ```
  SSL
  status = UNKNOWN
  blocked_by = dns_resolution
  ```
  ```
  STARTTLS
  status = NOT_APPLICABLE
  blocked_by = mx_missing
  ```
- Собственная техническая причина отказа самого чека фиксируется отдельным `reason_code`, никакой связи с другими чеками здесь нет:
  ```
  RDAP
  status = UNKNOWN
  reason_code = timeout
  ```
  ```
  Blacklist
  status = UNKNOWN
  reason_code = provider_unavailable
  ```

Без этого разделения `blocked_by` со временем начнёт одновременно выполнять роль dependency graph, error code и текстового объяснения — три разных назначения в одном поле.

### 2.2 Модель зависимости чеков

Ключевой принцип: **чек, который технически не мог быть выполнен из-за сбоя другого чека, не получает собственный независимый штраф.**

```
DNS A/AAAA → FAIL
    ↓ blocked_by: dns_resolution
SSL → UNKNOWN (не FAIL — проверка применима, но технически не могла быть выполнена)
```

Аналогично: если MX-запись отсутствует, чеки, объектом которых является принимающий почтовый сервер (STARTTLS, PTR, Blacklist), не становятся отдельными `FAIL` — это `NOT_APPLICABLE` (не `UNKNOWN`, потому что дело не в техническом сбое, а в отсутствии самого предмета проверки — почтового сервера) с `blocked_by: mx_missing`. SPF/DMARC/DKIM в эту группу не входят — это DNS-политики домена-отправителя, не зависящие от MX, и проверяются независимо. Без разделения на группы система либо наказывает домен дважды за одну и ту же первопричину, либо необоснованно блокирует чеки, которые от MX не зависят.

Каждый чек в реализации должен явно объявлять свои зависимости (`depends_on: [...]`), а не проверяться в вакууме.

### 2.3 Принципы Health Score (формула — отдельная задача реализации, не финализируется здесь)

Фиксируются сейчас как ограничения, которым обязана подчиняться любая конкретная формула:
- **В score участвуют только чеки со `status = FAIL`. Severity определяет размер штрафа. `PASS`, `UNKNOWN` и `NOT_APPLICABLE` не уменьшают score** — это разрешает неоднозначность, которая иначе возникает из независимости осей status/severity (например, `PASS + severity: informational` — по этому правилу однозначно не штрафуется):
  ```
  FAIL + critical       → штраф
  FAIL + warning        → штраф
  FAIL + informational  → небольшой штраф

  PASS + любая severity → 0
  UNKNOWN               → 0, но снижает индикатор confidence
  NOT_APPLICABLE        → 0
  ```
  Решение о том, является ли конкретное состояние (например, отсутствие AAAA) `PASS` или `FAIL + informational`, принимается на уровне конфига конкретного чека при реализации — сам принцип "штраф только за FAIL" от этого решения не зависит
- Score не может быть ниже 0 (floor)
- Один и тот же корневой дефект не штрафуется дважды — обеспечивается моделью зависимости из 2.2, а не отдельной логикой в формуле score
- Веса severity (Critical / Warning / Info) и точный список чеков на каждом уровне — фиксируются в конфиге на этапе реализации MVP, не хардкодятся по ходу разработки

## 3. Набор проверок

### MVP 1.0 — граница зафиксирована, не расширяется
IDN pipeline + DNS (resolver comparison) + Registry (`registryProvider`) + SSL + Health Summary + security foundation (SSRF-guard). Email Health, HTTP checker, reputation — сознательно не в этой границе, даже частично ("раз уж SPF простой") — это следующий шаг после MVP, а не довесок к нему.

| Проверка | Что показываем |
|---|---|
| **Preprocessing / IDN pipeline** | Обязательный шаг перед любой проверкой, единый канонический объект домена (раздел 4) |
| **DNS lookup** | A, AAAA, MX, TXT, NS, CNAME, SOA через несколько независимых публичных resolver'ов (Cloudflare/Google DoH). В PRD и коде называется **resolver comparison** — не "мультирегиональная проверка" и никогда не "DNS propagation worldwide" ни в одном UI-тексте, чтобы не создавать ложное обещание гео-распределения |
| **WHOIS / RDAP** | Через `registryProvider`, возвращает нормализованный результат (раздел 5) |
| **SSL/TLS check** | Фиксированный список, раздел 6 |
| **Domain Health Summary** | На базе status/severity модели, раздел 2 |
| Локализация | RU / UZ / EN с самого старта |

### MVP 1.1 — первое сильное расширение продукта
Email Health делится на три независимые группы, а не один блок с общей зависимостью от MX:

```
Email Authentication              — DNS-политики домена, не зависят от MX
├─ SPF   (multiple records, lookup count > 10)
├─ DMARC
└─ DKIM  (selector-эвристика, нужен selector)

Inbound Mail
├─ MX
└─ STARTTLS   — depends_on: MX

Mail Server / IP
├─ PTR         (включая отдельную пометку отсутствия IPv6 PTR)
└─ Blacklist   IP почтового сервера
```

Важно: SPF, DMARC и DKIM публикуются как DNS-записи домена-отправителя и существуют независимо от того, есть ли у домена MX — RFC 7208 прямо описывает `v=spf1 -all` как нормальную практику для доменов, которые вообще не отправляют почту. Если MX отсутствует — `NOT_APPLICABLE (blocked_by: mx_missing)` становится у проверок, объектом которых является принимающий почтовый сервер: **STARTTLS, PTR и Blacklist**. SPF, DMARC и DKIM проверяются независимо от наличия MX в любом случае.

**PTR и Blacklist относятся к MX-серверу, а не к исходящей почте.** MX определяет, какой сервер *принимает* почту для домена — сервер, с которого домен *отправляет* письма, может быть совершенно другим (отдельный relay/submission-инфраструктура). Поэтому PTR/blacklist-проверка IP из MX показывается как состояние принимающего сервера, а формулировки вида "ваша исходящая почта будет попадать в спам" на основании только этих данных недопустимы — для настоящей оценки outbound-репутации нужен именно sending IP, которого 2check на этом этапе не знает.

## 4. Preprocessing — канонический объект домена

Единый пайплайн на входе, единый объект на выходе — получают все последующие чеки, ни один не нормализует вход по-своему:

```
input → trim → lowercase → Unicode normalization → IDNA validation → ASCII/punycode
```

```
CanonicalDomain {
  originalInput: string
  unicodeHostname: string
  asciiHostname: string

  publicSuffix: string
  registrableDomain: string

  labels: string[]
  isIdn: boolean
}
```

Разделение hostname/registrable domain обязательно, иначе объект ломается на первом же вводе вроде `mail.example.uz` или `status.shop.example.co.uk`: DNS и SSL должны проверяться именно для введённого hostname. Пример:

```
input:              status.shop.example.co.uk
asciiHostname:       status.shop.example.co.uk
publicSuffix:        co.uk
registrableDomain:   example.co.uk

DNS  → canonicalDomain.asciiHostname
SSL  → canonicalDomain.asciiHostname
RDAP → registryProvider определяет registryDomain (раздел 5)
```

**`registrableDomain` (в `CanonicalDomain`) и `registryDomain` (определяется provider'ом, раздел 5) — разные понятия, не взаимозаменяемые.** Public Suffix List состоит из двух разных секций — ICANN и PRIVATE — и сам PSL прямо предупреждает, что разные приложения должны трактовать их по-разному. Для PRIVATE-записей (например, `foo.some-platform.example`) `registrableDomain`, посчитанный по PSL, корректен для web/cookie-семантики (границы изоляции между пользователями платформы), но это не значит, что `foo.some-platform.example` — отдельная регистрация в TLD-реестре: реальный зарегистрированный домен принадлежит владельцу платформы, а не её тенанту.

`registryDomain` **намеренно не входит в `CanonicalDomain`** — иначе возникает круговая зависимость: preprocessing формировал бы поле, для определения которого нужны правила конкретного registry-адаптера, а сам этот адаптер получает `CanonicalDomain` уже сформированным на входе (`registryProvider.lookup(canonicalDomain)`). Ответственность разведена однозначно: preprocessing ничего не знает о правилах конкретного реестра и отдаёт только `registrableDomain` (общая PSL-граница) как стартовую точку; `registryDomain` — вывод, который вычисляет и возвращает сам `registryProvider`-адаптер (раздел 5), а не вход, который он потребляет.

Это особенно важно с учётом того, что `.uz` — лишь первый provider, а архитектура не должна навсегда оставаться `.uz`-checker'ом (раздел 5).

Поле `tld` для этой цели не годится — реальная граница регистрации не всегда совпадает с последней label домена (как раз случай `co.uk`).

Пользователю показываются одновременно исходная и ASCII-форма (например, `оптика.uz` → `xn--80aikucn.uz`).

## 5. Registry — `registryProvider` и нормализованный результат

Контракт возвращает нормализованный результат, а не транспортные детали как основной интерфейс:

```
registryProvider.lookup(canonicalDomain)
    ↓ provider определяет registryDomain по правилам конкретного реестра
NormalizedDomainRegistration {
  registryDomain
  registrar
  createdAt
  expiresAt
  nameServers[]
  status
  registrant: {
    name:    value | redacted | unavailable
    email:   value | redacted | unavailable
    phone:   value | redacted | unavailable
    address: value | redacted | unavailable
  }

  raw: { rdap?, whois? }        // технический режим только
  freshness: {
    checkedAt              // обязательное
    cached: boolean        // обязательное
    cacheAge               // обязательное
    sourceUpdatedAt?       // nullable — не каждый RDAP/WHOIS источник отдаёт реальное время обновления данных реестра
  }
}
```

`raw.rdap`/`raw.whois` — вспомогательные поля для технического режима отображения, а не то, на чём строится основная логика domain-модуля. WHOIS и RDAP — это способы получения данных, а не то, что должно "протекать" в потребителя как обязательный контракт. Поля `registrant.*` доступны по отдельности — каждый источник может открывать часть данных (например, имя видно, а email `redacted`), и жёсткая модель "весь registrant либо доступен, либо скрыт целиком" этого не выражает.

**Продуктовое ограничение на отображение (не только форма данных):** даже когда конкретное поле `registrant.*` доступно (не `redacted`/`unavailable`), оно **не выводится в публичной сводке** — только в детальном/техническом режиме, за дополнительным действием пользователя (клик/капча). Сырой `raw.rdap`/`raw.whois` с персональными данными не должен становиться публично индексируемым контентом ни при каких обстоятельствах. Детали хранения, retention и конкретные юридические требования — предмет отдельной Security Specification, не этого документа.

**Freshness** показывается только в деталях (не на главном экране): "Проверено сейчас" / "Данные реестра получены 48 минут назад" — важно для доверия к WHOIS/RDAP-данным, которые могут быть закэшированы.

`.uz` — первый адаптер (`UzRegistryProvider`) за этим интерфейсом:
- WHOIS-сервер `whois.cctld.uz`, RDAP `rdap.cctld.uz` (`application/rdap+json`) — основной источник
- Регистрант может быть `redacted`/`unavailable` — UZINFOCOM указывает дифференцированный доступ к данным через RDAP
- Кэш обязателен, адаптивный TTL: активные домены 1–3 часа, grace/redemption period — минуты
- Кодировки легаси-ответов (CP1251/UTF-8) — требование к robustness парсера, не задокументированный факт

## 6. SSL/TLS check — фиксированный объём для MVP

Закрытый список, без cipher grading, BEAST/POODLE и десятков legacy-проверок:
- сертификат действителен/недействителен, совпадение hostname
- issuer, SAN, valid from/to, дней до окончания
- цепочка сертификатов, поддержка TLS 1.2/1.3
- просроченный intermediate, self-signed, недоверенная цепочка

При `blocked_by: dns_resolution` (домен не резолвится) — статус `UNKNOWN`, не `FAIL` (раздел 2.2).

## 7. Security / SSRF protection

Домен может резолвиться в loopback (`127.0.0.1`), приватные диапазоны (`10.0.0.0/8` и т.д.), облачный metadata-эндпоинт (`169.254.169.254`), приватные/link-local IPv6-диапазоны. Ограничение "принимаем только домены" само по себе не защищает.

**Правило (resolve-then-connect на зафиксированный IP, а не повторный resolve перед запросом):** простой повторный resolve непосредственно перед запросом оставляет окно для DNS rebinding — приложение проверяет безопасный IP, а затем HTTP/TLS-клиент самостоятельно резолвит hostname заново и получает уже другой адрес. Правильная последовательность:

1. Resolve hostname → получить все A/AAAA
2. Проверить **все** полученные IP по SSRF-политике (private/loopback/link-local/metadata диапазоны)
3. **Если хотя бы один IP в ответе запрещён — весь target считается подозрительным, сетевой check не выполняется целиком.** Не "выбрать разрешённый IP из смешанного набора и продолжить" — DNS-ответ вида "1 публичный + 1 приватный" блокируется полностью, а не частично пропускается. Нормальному публичному сайту незачем одновременно резолвиться и во внутренний адрес инфраструктуры 2check
4. Если все IP прошли проверку — выбрать один разрешённый и выполнить соединение именно с ним, не резолвя hostname повторно на этапе подключения
5. Для TLS — исходный hostname сохраняется в SNI и используется для проверки сертификата; для HTTP — исходный `Host`-заголовок сохраняется, но TCP-соединение идёт на уже провалидированный адрес

**Редиректы — отдельная точка обхода:** каждый следующий адрес в цепочке HTTP-редиректа проходит весь цикл (resolve → проверка IP → connect на зафиксированный IP) заново, а не разовую проверку на входе. Домен может честно пройти первичную проверку, а затем средиректить на `169.254.169.254` — без пере-валидации на каждом хопе guard тривиально обходится.

- **Google Safe Browsing API** — допустим, пока сервис строго некоммерческий. ToS ("not for sale or revenue-generating purposes") юридически размыт, доступ Google может отозвать без объяснений, SLA нет
  - Прячется за `reputationProvider.check(domain)` — миграция на Web Risk при появлении монетизации не требует переписывания бэкенда
- **Yandex Safe Browsing API** — Lookup (передаёт URL Яндексу, без гарантии времени ответа) или Update (локальная база, для масштаба)
- Опционально VirusTotal

## 9. Архитектура

- **DNS:** DoH-провайдеры, resolver comparison через несколько независимых резолверов (MVP), гео-распределение — фаза 2
- **Registry:** `registryProvider` → `NormalizedDomainRegistration` (раздел 5)
- **SSL:** TLS-хендшейк с сервера, SSRF-guard (раздел 7)
- **Reputation:** за `reputationProvider` (раздел 8)
- **Загрузка результата в MVP** — без SSE/WebSocket: фронт параллельно вызывает независимые эндпоинты, карточки переходят по статус-модели. SSE — позже, для комплексного скана из 15–30 проверок

**Стек:**
- Фронт: Next.js (SSR/ISR, минимум клиентского JS)
- Бэк: Node.js/Fastify или Python/FastAPI
- Кэш: Redis, адаптивный TTL
- Хостинг MVP: один VPS

## 10. Защита от абьюза

- Многоуровневая защита: мягкий IP-rate-limit → fingerprinting → Cloudflare Turnstile при подозрительной активности
- CGNAT мобильных операторов — комбинировать IP с cookie/session-токеном
- Домены на вход + обязательный SSRF-guard (раздел 7) — два разных уровня защиты, один не заменяет другой
- Логирование с учётом закона о персональных данных

## 13. Приоритизация (дорожная карта)
